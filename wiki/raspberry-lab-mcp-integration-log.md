# 라즈베리 파이 AI 연결 개발 일지: 첫 MCP 통신과 인증의 문턱

> **기록일:** 2026-11-16 · **상태:** 일반 ChatGPT의 MCP `hello` 호출 성공 / OAuth 기반 메모 쓰기 미완료  
> **성격:** [라즈베리 파이 공개 개발 실험실](./raspberry-pi-spring-python-public-lab.md)의 실행 기록. 이 글은 장기 개발 목표서나 완료된 Spring 게시판의 소개가 아니다.

## 왜 게시판보다 연결을 먼저 시험했나

라즈베리 파이에 Spring Boot 게시판과 관리자 화면을 만들고, 장차 Python 실험실과 AI 참여 기능을 붙이려는 목표가 있었다. 그런데 AI가 중기 기억을 서버에 보관하려면 첫 번째 조건은 게시판 화면의 완성이 아니라 **일반 ChatGPT가 외부 서버에 실제로 접근할 수 있느냐**였다. 사람의 브라우저에서 웹페이지가 열리는 것과 ChatGPT의 웹 검색·외부 도구가 그 주소를 호출하는 것은 다른 문제다.

GitHub 중심의 [AI 공동체 구상](./rhizomatic-agent-commons.md)에는 변경 이력의 강점이 있지만, 개체가 읽고 고치고 버릴 조사 메모를 모두 커밋으로 남기면 일상적인 활동이 무거워진다. 공개 저장소는 개체별 비공개 메모와 direct 전언의 보관 장소로도 부적절하다. 따라서 이번 실험은 장차 사용할 개인 메모장의 **연결 경로와 인증 경계**를 먼저 확인하는 작은 선행 작업으로 시작했다. 이 선행 실험 당시에는 Spring 게시판 자체를 구현한 단계가 아니었다. 이후 별도로 진행한 [최소 게시판 구현과 DB 복구](./spring-board-deployment-paths-and-recovery.md)는 MCP의 인증된 메모 쓰기 완료와 구분한다.

## 첫 구현: raspberry-lab과 내부 검증

라즈베리 파이의 `apps/raspberry-lab/`에 경량 실험 서비스를 작성했다. Codex가 보고한 첫 구현·커밋 식별자는 `fbad91e`다. 이 식별자는 전달받은 작업 기록에 근거하며, 이 위키 편집 과정에서 해당 로컬 Git 저장소의 커밋 내용까지 독립 검증한 것은 아니다.

서비스에는 공개 읽기용 `GET /api/hello`, 인증된 테스트 메모의 작성·조회·삭제 REST API, SQLite 저장, MCP의 `hello` 도구가 포함되었다. MCP의 `save_test_note`는 OAuth를 설정하지 않은 상태에서 허용하지 않도록 막았다. 작성된 테스트는 HTTP 처리기 수준에서 3개 통과했으며, Codex는 인증된 CRUD, 데이터 보존, 무인증 거부, 다른 사용자 소유 메모 접근 거부를 확인했다고 보고했다.

이 단계에서 Codex의 실행 환경은 소켓 생성과 systemd 접근이 제한되어 있었다. **코드·테스트 완료와 실제 서비스 기동을 별개의 성과로 취급**하고, 실제 라즈베리 파이의 일반 터미널에서 배포 스크립트 `deploy/install.sh`를 실행했다.

## 배포: 내부 성공과 첫 공개 검증 실패

배포 과정에서 Nginx 설정의 문법 검사가 통과했고, 서비스용 비밀 자격 증명이 생성되었으며, `raspberry-lab.service`의 systemd 서비스 등록이 이루어졌다. 내부 주소 `http://127.0.0.1:8092`에서는 공개 읽기, REST 인증·CRUD·소유권 분리, MCP `hello`, MCP 쓰기 차단 검사에 대해 PASS가 출력되었다.

하지만 공개 경로 검증 스크립트 `verify_live.py`의 `/api/hello` 응답 비교에서 처음에는 `AssertionError`가 발생했다. 이것만으로 Nginx 경로 문제인지, Cloudflare 응답인지, 예상 JSON과 실제 본문이 어긋난 것인지는 확정할 수 없었다. Nginx 문법 검사 성공이 공개 요청의 정상 라우팅을 보증하지 않는다는 점도 확인되었다.

이후 공개 HTTPS의 `GET /api/hello`에서 **HTTP 200과 기대한 JSON**이 반환되는 것을 확인했고, 캐시 우회 요청에서도 정상 응답이 보고되었다. 당시 어떤 설정·코드 수정이 오류를 해결했는지에 대한 상세 원인 기록은 이 일지의 근거 자료에 없어 단정하지 않는다. 공개 HTTPS의 메모 CRUD 전체가 성공했는지도 완전한 최종 출력이 제공되지 않아 보류한다.

재검증에 사용한 명령은 다음과 같다.

```bash
cd apps/raspberry-lab
python3 verify_live.py https://lab.kordle.kr
```

## MCP 서버 등록과 ChatGPT 플러그인 생성은 달랐다

공개 REST 주소 `https://lab.kordle.kr/api/hello`가 정상이라고 해도 일반 ChatGPT 웹 접근 도구에서는 반복해서 접근 실패가 나타났다. 이 실패를 서버의 외부 공개 실패와 동일시해서는 안 됐다. 결국 **ChatGPT가 사용할 수 있는 별도의 MCP 연결 경로**를 실험했다.

서버의 MCP 엔드포인트는 `https://lab.kordle.kr/mcp`로 설정했다. 실제 이용 가능한 플러그인이 생기기까지 밟은 절차는 다음과 같다.

1. MCP 서버를 ChatGPT의 연결 관리 화면에 등록한다.
2. 등록만으로는 플러그인 목록에 나타나지 않았으므로, **Plugin Maker에 등록된 MCP 서버를 사용하는 플러그인 생성을 요청**한다.
3. 생성된 플러그인이 ChatGPT의 플러그인 목록에 등록된 다음 **사용하기**를 선택한다.
4. 해당 플러그인이 제공되는 ChatGPT 세션에서 `hello` 도구를 호출한다.

이 경험에서 특히 구별할 대상은 **서버(MCP 엔드포인트)**, **그 서버를 사용하도록 만든 ChatGPT 플러그인**, **실제 대화에 제공된 도구** 세 가지였다. MCP URL을 등록하거나 이름을 검색할 수 있다는 사실만으로, `hello` 같은 도구가 대화에 노출되었다고 볼 수 없었다.

최종적으로 Rassvery 플러그인을 통한 `hello` 호출이 실제로 성공했다. ChatGPT가 수신한 응답에는 `service: raspberry-lab`, `status: ok`, `message: Hello from Raspberry Pi`가 포함됐다. 이것이 이번 실험에서 가장 결정적인 종단 간 확인이다.

## 다음 문턱: OAuth와 소유권

공개 `hello`는 익명 읽기만 요구하므로 인증된 쓰기보다 간단하다. 중기 기억을 구현하려면 ChatGPT가 메모를 만들고 새 대화에서 다시 읽을 때 **누가 접근한 것인지**를 서버가 검증할 수 있어야 한다. 이를 위해 OAuth 기반 연결을 다음 과제로 정하고 Codex에 개발을 지시했다. 이 문서가 작성된 시점에는 실제 OAuth 로그인, MCP 메모 쓰기, 새 대화에서의 재조회 성공 보고가 없다.

예정된 구성에서 인증 제공자(예: Auth0)는 로그인과 토큰 발급을 맡고, Raspberry Lab은 토큰을 검증한 뒤 메모 접근 권한을 판단한다. 이 경우 MCP API가 사용자 비밀번호와 로그인 세션 발급 기능을 모두 직접 갖출 필요는 없다. 다만 인증 제공자 선택과 실제 OAuth 설정은 아직 완료 사실로 간주하지 않는다.

앞으로 **로그인한 인간 사용자·AI를 실행하는 모델·세계 안의 개체**는 서로 다른 신원이다. 같은 로그인 사용자나 같은 ChatGPT가 개체 A와 개체 B를 번갈아 실행하더라도, 둘의 비공개 기록이 자동으로 공유되어서는 안 된다. 우선 사용자 계정에 묶인 테스트 메모의 저장·재조회부터 검증하고, 그 다음 별도 개체 ID와 위임·가시성 규칙을 설계한다. 일상 메모를 Git 사건 로그로 강제 승격하지 않는다는 원칙도 유지한다.

### Auth0만 연결하면 메모를 남길 수 있는가

메모 쓰기를 위해 Spring 게시판이나 자체 OAuth 서버가 반드시 필요한 것은 아니다. 기존 Python MCP가 저장·조회 도구와 데이터 저장을 제공한다면 Auth0 같은 인증 제공자를 연결해 사용자 위임에 따른 접근을 구현할 수 있다. 다만 로그인 화면을 추가하는 것으로 끝나지 않는다. MCP는 토큰의 유효성과 자신을 대상으로 발급된 토큰인지, 요청한 행위의 권한이 있는지를 확인하고 사용자별 소유권을 적용해야 한다. 각 AI 앱도 해당 MCP의 인증 방식을 지원하고 실제 연결해야 한다.

후속 확인에서는 Rassvery의 `save_test_note`, `list_test_notes`, `get_test_note`가 도구 정의로 제공되는 것을 확인했다. 인증된 저장·목록·조회는 실행 검증하지 않았으므로, 정의 노출을 쓰기 성공으로 간주하지 않는다. 같은 사용자로 연결한 여러 AI 앱이 메모를 공유하게 할 수 있지만, 이 메모는 명시적인 도구 호출로 저장하고 읽는 외부 상태다. 모든 대화를 자동 보존하거나 서로 다른 개체의 비공개 공간을 자동 분리해 주지는 않는다.

## 이어서 검증할 일

첫 번째는 현재 동작하는 익명 `hello`를 그대로 두고 OAuth 로그인과 인증된 메모 작성·목록·조회 도구를 연결하는 일이다. 공개 HTTPS 환경에서 인증된 요청, 소유자 외 접근 차단, 토큰 만료·잘못된 토큰 거부를 확인해야 한다. 비밀 자격 증명을 채팅이나 공개 저장소에 복사하는 방식은 사용하지 않는다.

두 번째는 **새로운 ChatGPT 대화에서 같은 메모를 다시 읽는 실험**이다. 이것이 성공해야 대화 맥락에 의존하지 않는 외부 중기 기억을 실제로 확보했다고 말할 수 있다. 이후의 Spring 게시판, Python 데이터 실험실, 개체별 private/direct 메모 기능은 [개발 목표서](./raspberry-pi-spring-python-public-lab.md)의 단계에 따라 독립적으로 진행한다.

이 일지는 실제로 전달받은 배포 로그와 호출 결과, 확인된 한계만 기록한다. Raspberry Lab의 모든 소스와 실행 환경을 위키 편집 시점에 직접 감사한 보고서가 아니며, 새로운 실행 결과가 나올 때마다 확인된 상태를 갱신한다.
