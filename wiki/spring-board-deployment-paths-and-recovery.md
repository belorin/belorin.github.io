# 작은 Spring 게시판의 첫 배포: JAR, DB 경로, SSH 터널과 관리자 복구

Java 프로그램이 서버에서 시작됐다는 사실과, 같은 데이터를 보면서 안정적으로 운영된다는 사실은 다르다. 초소형 게시판의 첫 배포에서는 코드보다 실행 위치와 데이터 경로가 더 큰 혼선을 만들었다. 같은 주소에서 같은 아이디로 가입했는데도 서로 다른 DB에 계정이 만들어졌고, 저장된 비밀번호와 관리자 권한도 어긋났다. 이 사례는 배포를 실행 파일 복사만으로 이해할 때 빠지는 조건을 보여 준다.

이 글은 2026년 11월 16일 확인된 Mac 개발·테스트 결과와 Raspberry Pi의 실행 출력, 사용자 동작 확인을 바탕으로 한다. 서버의 모든 설정을 직접 감사한 보고서는 아니며, 공개 인터넷 연결과 systemd 등록의 최종 성공은 확인 범위에 포함되지 않는다. 내부 주소·실제 계정 경로·자격 증명은 공개하지 않고 경로 예시는 일반화한다.

## 작은 기능부터 시작한 개발 환경

처음 목표는 Java 21, Spring Boot, Spring Security, Thymeleaf로 회원가입·로그인과 글쓰기가 되는 작은 게시판을 만드는 것이었다. 기존 Python MCP와 Rassvery는 유지하고, OAuth 서버·GitHub Actions·자동 배포를 첫 구현에 넣지 않았다. Mac에서 코드를 만들고 테스트한 뒤, 라즈베리에는 실행에 필요한 결과물만 보내는 방식으로 범위를 줄였다.

개발 Mac은 Apple Silicon arm64, macOS 15.1.1이었다. 초기 여유 공간은 약 97GiB였으며 기존 Git과 로그인된 Codex CLI를 재사용했다. 시스템의 기본 Java 명령은 실행 환경을 찾지 못했지만, 추가 점검에서 Homebrew Java 17.0.2가 약 307MiB 설치돼 있음을 확인했다. 명령이 실패한다는 이유만으로 설치 자체가 없다고 단정할 수 없었다. 기존 Java는 그대로 두고 승인 후 프로젝트 폴더에 Temurin Java 21.0.13과 Maven 3.9.11을 설치했다.

| 프로젝트 추가 구성 | 측정된 사용량 |
| --- | --- |
| Java 21 JDK | 약 335MiB |
| Maven | 약 10MiB |
| 프로젝트 전용 의존성 캐시 | 약 77MiB |
| 빌드 결과 | 약 29MiB |
| 첫 프로젝트 전체 | 약 452MiB |

이는 첫 구현 시점의 측정값이지 이후 데이터 증가까지 포함한 고정 비용은 아니다. 다운로드한 설치 압축파일은 체크섬 검증·추출 후 정리했고, 기존 도구와 캐시는 임의로 지우지 않았다. 별도 IDE, Docker, Node 패키지, DB 서버도 설치하지 않았다. JDK는 개발·빌드에, 서버의 Java 실행 환경은 만들어진 JAR 실행에 쓰므로 두 장치에 같은 도구를 모두 설치할 이유는 없었다.

## 구현한 기능과 검증의 범위

첫 구현은 Spring Boot 3.5.16, Spring Security, Thymeleaf, JDBC와 파일형 H2를 사용했다. 장기 구상에 있던 JPA·SQLite·MariaDB와 달리, 최소 구현에서는 별도 DB 서버 없이 시작했다. 회원가입·로그인·로그아웃, 최근 50개 글 목록, 상세 읽기, 로그인한 회원의 글 작성을 만들었다.

비밀번호는 BCrypt로 해싱하고 CSRF 방어를 유지했다. 작성자는 요청으로 전달받은 이름이 아니라 로그인한 세션에서 결정했으며, 게시글 출력에는 Thymeleaf의 이스케이프 기능을 사용했다. 일반 가입으로 관리자 역할을 선택할 수 없도록 했다.

관리자 화면에는 회원·전체 글·숨긴 글의 통계, 회원 목록, 게시글 숨기기와 다시 공개 기능을 추가했다. 숨김은 목록에서 제외하는 데 그치지 않고 상세 주소도 404로 처리한다. 삭제 대신 복원이 가능한 방식으로 첫 관리 기능을 제한했다. 관리자 목록은 50개 단위로 나눴다. 일반 회원은 관리자 URL을 직접 입력하거나 관리 요청을 보내도 거부된다.

기본 테스트 8개와 관리자 테스트 5개, 총 13개가 통과했다. 가입 중복·잘못된 입력·비밀번호 해싱·오로그인·비회원 글쓰기 차단·CSRF·HTML 이스케이프·없는 글·관리자 접근·숨김과 복원·가입 시 역할 위조 등을 확인했다. Mac 브라우저에서는 가입부터 글쓰기·로그아웃까지, 서버 재시작 후 계정과 글 보존도 확인했다. 이 테스트 성공을 Raspberry Pi의 공개 HTTPS·서비스 등록·재부팅 검증까지 완료했다는 뜻으로 확장해서는 안 된다.

## JAR 실행과 데이터 생성은 다른 일이다

JAR는 ZIP 계열의 아카이브이지만, 실행한다고 프로젝트 전체를 설치 폴더에 두 벌씩 풀어놓는 것은 아니다. Java가 아카이브 안의 프로그램과 라이브러리를 사용해 프로세스를 시작한다. 애플리케이션이 필요에 따라 만드는 DB·로그·임시파일은 실행 파일 자체와 구별해야 한다.

이번에 두 곳에 생긴 것은 게시판 코드 사본이 아니라 H2 데이터 파일이었다. 관리 작업을 위해 JAR 안의 H2 라이브러리 하나를 별도 도구로 추출한 일도 있었지만, 그것은 게시판을 한 벌 더 배포한 것과 다르다.

배포에는 적어도 세 가지가 필요하다. 실행할 프로그램의 위치, 데이터를 보관할 위치와 설정, 그리고 프로세스의 시작·종료·재시작을 맡을 방법이다. JAR를 바꾸는 업데이트와 회원·게시글 DB를 바꾸는 작업은 서로 독립적으로 다뤄야 한다.

## 같은 URL인데 계정이 달라진 이유

초기 DB 설정은 상대 경로인 `jdbc:h2:file:./data/board`였다. 여기서 기준점은 JAR 파일이 놓인 폴더가 아니라 **프로세스의 현재 작업 디렉터리**다.

| 실행한 위치의 예 | 실제로 열리는 파일의 예 |
| --- | --- |
| `/home/operator` | `/home/operator/data/board.mv.db` |
| `/home/operator/tiny-board` | `/home/operator/tiny-board/data/board.mv.db` |

두 프로세스를 동시에 띄운 것이 아니어도, 같은 JAR를 종료한 뒤 다른 폴더에서 같은 포트로 실행하면 브라우저 주소는 같고 DB만 달라질 수 있다. 자동 생성이 허용돼 있으면 새 위치에 빈 DB가 생긴다. 사용자에게는 계정이 사라졌거나 같은 아이디로 다시 가입되는 현상으로 보인다.

실제 조회에서는 두 DB 모두 관리자용으로 선택한 같은 아이디가 있었지만 역할은 USER였다. 첫 DB에는 글이 한 개, 두 번째 DB에는 글이 없었다. 앞서 관리자 권한 변경 명령이 반환한 `Update count: 0`은 삭제 결과가 아니라, 그때 선택한 DB에 변경 대상 계정이 없었다는 결과였다. 이후 두 번째 DB에도 다시 가입하면서 같은 아이디가 양쪽에 존재하게 됐다.

이 문제를 진단할 때는 화면의 이름이나 접속 포트만 보지 않는다. 실행 프로세스의 명령행, Linux의 `/proc/<PID>/cwd`, 실제 DB 파일 위치, 각 DB의 계정과 글 개수를 대조한다. SQL이 실행됐다는 사실만으로 의도한 DB와 행을 변경했다고 판단하지 않고, 변경 행 수와 변경 후 조회를 함께 확인한다.

## 원래 데이터를 보존하며 로그인과 권한을 복구한다

복구의 기준은 새 DB를 덮어쓰거나 계정을 반복 생성하는 것이 아니라, 보존할 데이터가 있는 원본을 먼저 선택하는 것이다. 이 사례에서는 글 한 개가 있는 첫 DB를 기준으로 정하고 두 DB를 모두 백업했다. 파일형 H2의 단순 파일 복사는 애플리케이션을 정상 종료해 DB가 닫힌 뒤 수행했다.

관리자 지정은 아이디의 문자열과 별개의 문제다. `admin`이라는 이름으로 가입해도 기본 역할은 USER이며, 운영자가 기존 계정의 역할을 ADMIN으로 바꿔야 한다. 변경 결과가 한 행인지 확인하고, 서버 재시작 후 다시 로그인해 새로운 역할을 반영했다.

비밀번호 문제는 같은 주소에서 동일 아이디로 두 차례 가입하면서 발생했다. 브라우저 비밀번호 관리자는 두 번째 가입 때의 비밀번호를 보관하고 있었지만, 사용할 첫 DB에는 처음 가입한 비밀번호 해시가 남아 있었다. 동일 애플리케이션·동일 BCrypt 형식·동일 사용자가 소유한 두 계정임을 확인한 이 복구에서는, 두 번째 계정의 해시만 첫 계정의 비밀번호 필드로 옮겨 현재 알고 있는 비밀번호를 재사용했다. 첫 DB의 글과 관리자 역할은 유지했다.

이 조치는 모든 시스템에 통용되는 비밀번호 복구 방식이 아니다. 계정 소유권과 해시 호환성을 확인한 운영자 작업이며, 비밀번호 원문이나 해시를 공개 문서·채팅에 출력하지 않았다. 일반 서비스의 비밀번호 재설정 기능과도 구별한다. 복구 후 로그인 정상 동작이 확인됐다.

최종 실행은 선택한 DB의 **절대 경로**를 명시하고 `IFEXISTS=TRUE`를 사용하도록 수정했다. 경로가 틀렸을 때 또 빈 DB를 만드는 대신 실패하게 하는 장치다. 처음 새 DB를 만들 때 사용하는 옵션과, 이미 존재하는 운영 DB를 고정해 실행하는 옵션은 구분해야 한다.

### 로그인 중 403은 별도로 진단한다

로그인 과정에서 Forbidden 403 화면도 관찰됐지만, 당시 요청 URL과 서버 로그가 확보되지 않아 원인은 확정하지 않았다. 서버 재시작 전에 열어둔 로그인 폼의 CSRF 토큰 문제와 일반 회원의 관리자 경로 접근은 서로 다른 후보였다. 새 로그인 화면에서 재시도하고 어느 요청에서 거부됐는지 확인해야 하며, 403 자체를 계정 삭제나 DB 손상의 증거로 삼아서는 안 된다.

## SSH 터널: 서버와 접속 통로를 따로 이해하기

라즈베리에는 Java 21.0.13의 64비트 ARM 실행 환경을 설치했고, 당시 남은 디스크는 약 3.8GB였다. Mac에서 만든 약 29MB JAR를 전송해, 기존 서비스와 겹치지 않는 8081 포트와 루프백 주소에 바인딩했다. 실행 로그에는 내장 Tomcat 시작과 `Started BoardApplication`이 출력됐으며, 이후 브라우저 접속과 로그인·로그아웃이 확인됐다.

Mac에서 사용하는 SSH 전달 명령의 구조는 `ssh -N -L 18081:127.0.0.1:8081 USER@PI_HOST`다. 이 예에서 USER와 PI_HOST는 실제 접속 계정과 호스트로 치환한다. `-N`은 원격 명령 실행 없이 통로를 유지하고, `-L`은 Mac의 18081 포트로 들어온 요청을 SSH 연결 너머 라즈베리의 루프백 8081로 전달한다.

따라서 두 프로세스의 역할이 다르다. 라즈베리의 Spring 프로세스가 게시판을 제공하고, Mac의 SSH 프로세스가 접속 통로를 유지한다. Spring을 종료하면 서버가 멈추고, 터널을 종료하면 서버가 살아 있어도 그 경로로는 접속하지 못한다. 명령 실행 뒤 터미널이 돌아오지 않고 기다리는 것은 서버나 터널이 동작 중일 때의 정상 상태일 수 있다.

이 구성에서 Mac 브라우저는 `http://127.0.0.1:18081`로 접속한다. 게시판의 루프백 주소를 공용 네트워크에 직접 노출하지 않고 확인할 수 있지만, SSH 터널 성공은 도메인을 통한 공개 HTTPS 배포 성공과 같지 않다.

## systemd와 기존 홈페이지를 보존하는 공개 연결

터미널을 닫아도 서버를 유지하려면 별도의 서비스 관리가 필요하다. 제안한 systemd 설정은 실행 사용자, WorkingDirectory, Java와 JAR의 절대 경로, 고정된 DB URL, 실패 시 재시작, 재부팅 시 시작 대상을 명시했다. `systemctl start`는 지금 실행하는 동작이고 `systemctl enable`은 부팅 시 시작하도록 등록하는 동작이다. 서비스 등록만으로 브라우저 접속용 SSH 터널까지 대체되는 것은 아니다.

설정과 등록 명령은 준비했지만 최종 `active (running)`, enable 결과와 실제 재부팅 후 재접속 결과는 아직 확인되지 않았다. 서비스 등록을 완료 사실로 기록하지 않는 이유다. 두 번째 DB와 백업도 서비스 전환 확인 후 정리할 대상으로 남았으며, 삭제 완료는 보고되지 않았다.

기존 Nginx에는 루트 홈페이지, 별도 Python 실험 경로, MCP·일부 API 경로가 이미 존재했다. 게시판을 공개한다는 이유로 `/`의 목적지를 바꾸면 홈페이지와 충돌한다. 따라서 기존 경로를 보존하고 별도 서브도메인을 사용하는 안을 제안했다. 하위 경로에 두는 것도 가능하지만, 현재 앱의 `/login`, `/posts` 등 루트 기준 경로를 함께 조정하고 검증해야 한다.

Nginx의 일부 조회 출력만으로 HTTPS 종료 지점이나 도메인 앞단의 터널 구성을 확정할 수는 없었다. 별도 호스트명은 제안 상태이며 DNS·터널·프록시를 변경하거나 게시판을 공개한 단계가 아니다. 기존 Python MCP와 홈페이지 설정을 유지한다는 원칙은 계속 적용된다.

## 메모를 남기는 AI에 Spring 게시판이 꼭 필요한가

사람이 이용하는 게시판과 AI의 외부 메모 저장은 관련될 수 있지만 서로의 필수 선행 조건은 아니다. 이미 Python MCP에 메모 도구와 저장소가 있다면, 인증 제공자를 연결하고 서버가 토큰·권한·소유권을 확인하도록 만드는 경로가 가능하다. 별도 Spring OAuth 서버나 게시판 화면을 먼저 완성해야 하는 것은 아니다.

현재 Rassvery에는 `save_test_note`, `list_test_notes`, `get_test_note`가 도구 정의로 노출돼 있었다. 이 사실은 실제 인증된 쓰기와 재조회까지 성공했다는 뜻은 아니다. Auth0는 로그인과 토큰 발급을 맡을 수 있지만, Python MCP의 토큰 검증과 사용자별 데이터 분리, AI 클라이언트의 인증 지원·연결은 별도로 필요하다.

같은 사용자로 인증된 여러 AI 앱이 같은 메모에 접근하는 구조와, 개체마다 비공개 기억을 분리하는 구조도 다르다. 후자는 개체 ID·위임·가시성 규칙이 추가돼야 한다. 도구 호출을 통해 저장·조회하는 외부 메모는 대화 전체를 저절로 영구 기억하는 기능이 아니다. 인증과 후속 검증은 [MCP 연결 일지](./raspberry-lab-mcp-integration-log.md)에서 이어 다룬다.

## 확인된 결과와 남은 일

| 항목 | 확인 범위 |
| --- | --- |
| Mac의 최소 게시판·관리자 구현 | 빌드 및 13개 테스트 통과 |
| Raspberry Pi Java 21·JAR 기동 | 버전·시작 로그 확인 |
| SSH 터널을 통한 브라우저 사용 | 페이지·로그인·로그아웃 확인 |
| 상대 DB 경로 문제 | 두 파일과 서로 다른 글 개수로 확인 |
| 관리자·비밀번호 복구 | 원본 DB 선택·절대 경로 지정 후 로그인 정상 확인 |
| systemd 상시 실행 | 설정과 명령 준비, 최종 상태·재부팅 검증 미확인 |
| 두 번째 DB 정리 | 보존 상태, 삭제·보관 이동 완료 미확인 |
| 기존 홈페이지와 분리된 공개 주소 | 제안 단계, 설정 변경 없음 |
| Auth0 기반 MCP 메모 쓰기 | 도구 정의 확인, 인증된 저장·재조회 미검증 |

초기 기능은 글 수정·삭제·댓글·검색·관리자 감사 로그까지 모두 포함하지 않는다. 운영 기능과 공개 연결을 확대할 때도 구현한 부분, 명령만 준비한 부분, 실제로 확인한 결과를 분리해 기록한다.
