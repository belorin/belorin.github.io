# 음악 취향 실험 — 5초·10초 단위의 생성과 개정

**성격:** [수리취향학](../../wiki/mathematical-theory-of-taste.md)과 [취향계산기 어댑터](../../wiki/taste-calculator-adapter.md)의 음악 매체 확장. [인물 이미지 L1–L3](../characters/L1-L3.md)와 같은 세 층을 사용하되, 음악의 시간적 구조와 편집 가능한 작곡 소스를 별도 취급한다. 이는 **운영 설계와 상태 기록 도구**이며 여기서 음원이 자동 작곡되거나 재생되는 것은 아니다.

## 시작하는 말은 짧게

새 대화에서 다음처럼 말할 수 있다.

> 이 [곡 상태 링크]를 읽고, 취향계산기 방식으로 **00 음악**의 다음 5초를 수정하자.

혹은

> [상태 파일]과 [오디오 또는 Poser 소스 링크]를 기준으로 00 음악을 계속 발전시키자. 이번에는 10초 구간만.

이때 에이전트는 링크로 실제 접근할 수 있는 파일과 기록을 먼저 확인한다. 존재하지 않는 음원이나 과거 청취 경험을 지어내지 않는다. 파일의 `song_id`, 현재 버전 `head`, 해당 버전의 출처와 오디오, 평가 사건, 다음 편집 의도에서 시작한다. 요청에 구간이 지정되지 않았으면 `next_focus`를 우선한다. 기본 첫 단위는 **5초**이고 사용자가 10초를 지정하면 **10초**를 쓴다.

## L1 → L2 → L3

| 층 | 음악에서 하는 일 | 보존 단위 |
| --- | --- | --- |
| **L1: 생성·청취·반응** | 5초 또는 10초짜리 독립 스케치 생성, 짧은 구간 청취, 또는 기존 곡의 특정 구간 편집. 감상은 채팅의 자유로운 한국어로 받음 | 작품 버전, 초 단위 구간, 자연어 반응, 실제 산출물 링크 |
| **L2: 잠정 취향·작품 상태** | 다봉우리 취향 가설, 예상 밖의 매력, 반복 청취와 실제 질림을 분리. **작품 수정의 목적**과 **사용자 취향 탐사의 목적**을 분리 | 노출 이벤트, 선호와 미확실성, 생성기 실패, 다음 편집 의도 |
| **L3: 위키·작곡 소스·계보** | 실험 규약, 작곡 YAML/Python 또는 DAW 프로젝트, 음색 설정, 렌더, 개정 트리, 검증 기록 | 버전별 원본·자식·오디오·분석 보고서, 불변 경로 또는 커밋 참조 |

여기서 L1/L2/L3는 시스템의 운영 층이며 FOUNDATIONS의 요소/스타일/객체를 구별하는 세 분석층과 다르다.

## 5초 또는 10초는 왜 중요한가

처음부터 60초를 매번 재생성하면 비용이 커진다. **5초·10초를 완성 가능한 작은 작곡 단위**로 삼으면 감상의 부담도 낮다. 곡 전체가 아니라 이 짧은 조각 자체를 작곡·렌더링할 수 있다. Poser에서 전체 길이 60초인 곡을 렌더링한 뒤 5초만 잘라 듣는 것은 **감상 시간만 줄이지 렌더링 비용까지 줄여주지는 않는다**. 이 둘을 구분한다.

- `sketch`: 처음부터 5초·10초 짜리 새 곡 파일을 만들고 렌더링한다.
- `revision`: 기존 곡의 특정 시간 구간을 수정하되 문맥(앞/뒤 부분, 전환, 모티프)을 반드시 검토한다. 구간 교체가 원곡의 전체적 매력을 파괴할 수 있다.
- `variation`: 같은 부모 곡을 서로 다른 방향으로 발전시키는 **형제 버전**을 만들고 결과를 비교한다. 반드시 최신 버전에서만 파생할 필요는 없다.
- `exploration`: 최근 좋아한 곡을 복제하지 않고 다른 음악적 체제의 독립 스케치를 제시한다. 새로운 봉우리를 찾는 실험이며 기존 곡의 수정 이력과 구분한다.

짧은 루프가 완성곡 전체의 만족을 대표한다는 가정은 하지 않는다. **짧은 매력을 가진 조각과 전체 곡의 매력은 별개의 관측**이다.

## 반복과 포화의 분리

이전 이미지 실험의 '호감 후 복제' 실패는 음악에서도 반복될 수 있다. 좋아한 음색·코드 진행·리듬을 곧장 다음 스케치에 재사용하지 않는다. 실제 청취에서 관찰된 **반복 횟수**와 사용자에게서 확인된 **지루함·질림의 반응**을 별도로 기록한다. 익숙해짐과 질림은 모두 가능하고, 동일 곡을 다시 들었을 때 반응이 달라질 수 있다.

음악은 더 강한 조건을 갖는다. 처음 싫었던 0~5초가 다음 5~10초의 긴장을 준비했다면 그 앞부분만 제거하는 수정은 전체를 나쁘게 만들 수 있다. 따라서 수정을 제안할 때는 구간에 대한 반응뿐 아니라 그 구간의 **전체 작품 속 역할**을 별도로 기록한다.

## 상태 파일: 무엇을 링크할 것인가

[상태 JSON 스키마](./song.schema.json)와 [빈 상태 예시](./song-template.json)가 있다. 저장하려는 실제 곡에 따라 파일을 복사해 `song_id`, `title`, `head`, `versions`, `listens`를 채운다. 이 파일은 *나중에 링크 하나로 다시 시작하기 위한 계약*이다. 다만 링크가 살아 있는지, 어떤 사용 권한이 있는지는 접근할 때마다 확인해야 한다.

- **고정 곡 ID**: 예를 들어 `music-00` 같은 식별자. 파일 이름·제목이 바뀌어도 유지한다.
- **버전의 부모**: `v000`에서 `v001`과 `v002`가 갈라지는 것도 허용한다. 부모와 기존 버전 기록은 삭제하지 않는다.
- **실제 소스**: Poser YAML/Python, 관련 Surge XT 프리셋/스튜디오 설정, 특정 커밋 또는 읽을 수 있는 파일 링크.
- **실제 음원**: WAV/MP3와 검증 가능한 고정 파일 링크. 가능하면 SHA256과 분석 보고서도 포함한다.
- **초 단위 부분**: `start_sec`와 `duration_sec` (처음에는 5 또는 10, 필요하면 다른 길이도 허용). 감상 대상과 수정 대상 구간을 혼동하지 않는다.
- **반응과 작업 의도**: 자유 반응은 원칙적으로 별도 L2 파일에 저장한다. 공개 위키/저장소에 사용자별 취향 데이터를 승인 없이 넣지 않는다.
- **보존 상태**: `planned`, `source-linked`, `rendered`, `auditioned`를 구분한다. 파일 이름만 보고 '청취 완료'라고 주장하지 않는다.

### 명령행 도구

Node.js 외부 의존성 없이 [`music.mjs`](./music.mjs)을 실행한다. 이 명령은 **곡을 실제로 작곡하거나 합성하지 않는다**. 리비전 링크, 기간, 응답과 다음 작업 지시문을 기록한다.

```bash
node taste-lab/music/music.mjs init /private/music-00.json music-00 "곡 제목"
node taste-lab/music/music.mjs attach /private/music-00.json v000 --source "https://.../songs/song.yaml" --audio "https://.../mix.wav"
node taste-lab/music/music.mjs plan /private/music-00.json --parent v000 --start 0 --duration 5 --intent "도입부를 다른 접근으로 개정"
node taste-lab/music/music.mjs attach /private/music-00.json v001 --source "https://.../songs/song-v001.yaml" --audio "https://.../v001.wav"
node taste-lab/music/music.mjs react /private/music-00.json v001 --start 0 --duration 5 --reaction "흥미롭지만 너무 갑작스럽다"
node taste-lab/music/music.mjs resume /private/music-00.json
node taste-lab/music/music.mjs validate /private/music-00.json
```

`--source`와 `--audio`는 실제로 존재하는 경로만 넣는다. 빈 파일을 처음 만들었다고 실제 곡 `music-00`이 존재한다고 주장하지 않는다. `resume`은 다음 채팅에서 사용할 **짧은 인계문**을 출력하며, 사용자가 채팅에 붙여 넣거나 상태 링크를 제공할 수 있다.

### Poser / Surge XT에 맡기는 영역

[Poser 공식 설정 안내](https://github.com/isnbh0/poser/blob/main/docs/setup.md)에 따르면 소스 파일을 YAML/Python으로 작성하고, `render-song`과 `analyze-song`으로 WAV·분석 보고서를 만든 뒤 `export-song`으로 배포 가능한 묶음을 내보낼 수 있다. 이 프로젝트의 상태 파일에 Poser의 소스 경로/버전/보고서/오디오를 연결한다. 동일 트랙의 변경만 재렌더링할 수는 있지만 **시간 구간 단위로 자동 부분 렌더링을 보장한다고 쓰지 않는다**.

이전 Binary Arcana 테마의 1분 데모 요청은 있었지만 **완성 음원, 파일명, 출처는 이 설계 시점에 확인되지 않았다**. 따라서 임의의 `music-00` 곡이나 MP3가 완성되었다고 등록하지 않았다. 실제 파일 또는 공개할 위치가 정해지면 그 곡의 첫 상태를 만드는 것부터 시작한다.

## 개발 원칙 및 완료 기준

- 링크 하나를 받은 세션이 **실제 곡 ID, 오디오와 소스 접근성, 가장 최근/선택된 버전, 5초·10초 구간, 반응, 다음 작업**을 구별할 수 있다.
- 기존 버전을 덮어쓰지 않는다. 곡의 모든 개정판을 하나의 목록으로 이어놓지 않고 **부모가 명확한 계보**로 관리한다.
- 버전의 오디오가 없으면 청취했다고 기록할 수 없고, 실제 반응이 없으면 `auditioned`라고 기록하지 않는다.
- 장기 기억의 자동 보존과 장기 저장소를 동일시하지 않는다. 실제 파일/상태 스냅샷이 재개를 가능하게 하는 기준이다.
- 공개 위키에는 방법·데이터 계약·검증 코드를 두고, 개인별 실제 평가 기록과 비공개 작곡 소스는 공개 승인을 받기 전까지 별도로 보존한다.
